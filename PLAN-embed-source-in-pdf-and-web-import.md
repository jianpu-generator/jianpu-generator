# PLAN: PDF embedding + web Import button (PR 2 of 2)

## Goal

Building on PR 1 (`PLAN-embed-source-in-svg.md`, which embeds `.jianpu`
source into SVG output and adds `extract_embedded_source` in Rust), this PR:

1. Extends source embedding to PDF export.
2. Exposes extraction through wasm-bindgen.
3. Adds an "Import" button to the web editor that lets a user pick a
   previously exported `.svg`/`.pdf` file and recover the original source
   text into a new editor file.

**Prerequisite**: PR 1 must be merged first — this plan assumes
`extract_embedded_source(svg: &str) -> Option<String>` and the embed-on-render
plumbing described there already exist.

## Part A — PDF embedding (Rust core)

### Open question to resolve first

PDF is generated by serializing to SVG string, then parsing that string
through `usvg::Tree::from_str` (`src/pdf.rs:46`), then `svg2pdf::to_chunk`
(`src/pdf.rs:56`) assembles the PDF via `pdf_writer`, embedding each page's
SVG as an XObject (`src/pdf.rs:36-93`).

`usvg` is a rendering-focused SVG subset parser — before writing any code,
write a throwaway test/script that renders an SVG containing the PR 1
`<metadata id="jianpu-source">` tag through `usvg::Tree::from_str`, then
through `svg2pdf::to_chunk`, and check whether the resulting PDF bytes still
contain the base64 payload somewhere recoverable (e.g. inside the embedded
XObject's SVG content stream). This determines which of the two approaches
below to take. Don't build both — pick one based on this check.

**If `usvg` preserves the `<metadata>` tag through to the embedded XObject:**
- No extra work needed beyond making sure PDF generation has the source
  string available to pass into SVG serialization before it gets fed to
  `usvg`. See "Threading source into the PDF CLI path" below.
- Extraction from PDF becomes: locate the embedded SVG XObject content stream
  inside the PDF bytes and run the same `extract_embedded_source` string
  search on it. May need PDF-stream-decompression handling if `pdf_writer`
  compresses XObject streams (check whether `Filter /FlateDecode` is applied
  — if so, extraction needs a flate-decompress step first).

**If `usvg` strips the `<metadata>` tag:**
- Embed source directly as PDF-native metadata instead — XMP metadata via
  `pdf_writer`'s metadata/XMP support (check `pdf_writer` crate docs/API for
  an XMP stream or `/Metadata` catalog entry), or a custom key in the PDF
  `/Info` dictionary as a simpler fallback (e.g. a custom `/JianpuSource` key
  — technically non-standard but PDFs tolerate unknown `/Info` keys fine, and
  the extractor only ever needs to talk to itself).
- Extraction from PDF: read the `/Info` dictionary or XMP stream instead of
  string-searching SVG-shaped content.

### Threading source into the PDF CLI path

`generate_pdf` (`src/cli/generate.rs:137-138`) currently calls
`jg::render_svgs(&score)` — the `Score`-only API with **no source string at
all** — then `jg::pdf::write_pdf(&svgs, ...)`. Unlike `generate_svg`, this
path never reads/keeps the raw source text.

Change `generate_pdf` to read the source file itself (mirroring
`generate_svg`'s pattern at `src/cli/generate.rs:194`, via
`super::read_source(&opts.input)`) and pass it down into a source-aware
render call, so the SVG pages handed to `write_pdf` already carry the
embedded metadata (in the `usvg`-preserves case), or so `write_pdf` itself
can accept the source string directly and write XMP/`/Info` metadata (in the
`usvg`-strips case).

### Testing

- Round-trip test: render fixture → PDF, extract, assert recovered text
  equals original source, matching the pattern from PR 1's SVG test.
- Test PDF generated via the plain `Score`-only path has no embedded source
  and extraction gracefully returns `None`.

## Part B — wasm-bindgen extraction function

- `crates/jianpu-wasm/` is the wasm-bindgen crate (built to `web/pkg/`,
  imported in the frontend as `jianpu-wasm`). Existing export-relevant
  bindings: `generate_pdf`/`generate_split_pdfs`
  (`crates/jianpu-wasm/src/lib_pdf.rs:18,45`), `generate_midi`/`generate_wav`
  in sibling files, `render`/`list_parts`/`compress_share_payload`/
  `decompress_share_payload` in `lib.rs`.
- Add a new file `crates/jianpu-wasm/src/lib_import.rs` (matches the existing
  `lib_pdf.rs`/`lib_midi.rs`/`lib_wav.rs` per-concern split) exposing:
  ```rust
  #[wasm_bindgen]
  pub fn extract_source_from_svg(svg_bytes: &[u8]) -> Option<String>
  #[wasm_bindgen]
  pub fn extract_source_from_pdf(pdf_bytes: &[u8]) -> Option<String>
  ```
  (or a single `extract_source(bytes: &[u8], is_pdf: bool)` — pick whichever
  matches the existing binding style in `lib_pdf.rs`/`lib_midi.rs`, check
  those files for the convention before deciding).
- `wasm_bindgen` return types: confirm whether existing bindings return
  `Option<String>` directly or use `JsValue`/`Result<String, JsValue>` for
  the "not found" case — match existing convention rather than introducing a
  new pattern.

## Part C — Web editor Import button

### Current state (no import mechanism exists today)

- `web/` is Vite + React + TypeScript. Editor is Monaco-based
  (`src/components/Editor.tsx`), orchestrated by `src/App.tsx` /
  `src/components/AppWorkspace.tsx`.
- Compute-heavy work (render/PDF/MIDI/WAV) runs in a Web Worker
  (`src/worker/jianpu.worker.ts`) that calls into the WASM module.
- Export UI: `src/components/ExportControls.tsx` (builds PDF/MIDI/WAV/"Export
  Parts" menu items) rendered via `src/components/ExportMenuButton.tsx`.
  Worker request plumbing: `src/hooks/useJianpuWorkerExports.ts` (builds
  `postMessage` requests) and `src/worker/exportMessageHandlers.ts`
  (worker-side handlers like `handleGeneratePdf`, each calling the
  wasm-bound `generatePdf(...)`).
- Files are managed via `src/fileStore.ts` +
  `src/storage/{localBackend,githubBackend}.ts` + `src/hooks/useFileOperations.ts`
  (create/duplicate/rename/delete — all backend-driven, no disk I/O today).
  There is **no** `<input type="file">`, `FileReader`, or
  `showOpenFilePicker` usage anywhere in `src/` currently — the closest
  existing "import-like" flow is the share-link mechanism
  (`src/shareUrl.ts`, `src/hooks/useSharedPreview.ts`, WASM
  `compress_share_payload`/`decompress_share_payload`), which is a different
  mechanism (URL-hash-encoded content, not file-based) but worth skimming for
  UI/UX conventions (e.g. how it surfaces a "load this content?" prompt).

### Design

- New `<input type="file" accept=".svg,.pdf">`-based picker — no existing
  pattern to reuse, this introduces the first disk-file-read in the app.
  Read the file as `ArrayBuffer` via `FileReader` (or `file.arrayBuffer()`,
  simpler with modern browser support — check what browser support baseline
  the rest of the app assumes, e.g. check `vite.config.ts`/browserslist
  before picking).
- New worker message types in `src/worker/messages.ts` (request: file bytes +
  whether SVG or PDF; response: extracted source string or a "not found"
  result).
- New `src/worker/importMessageHandlers.ts` (sibling to
  `exportMessageHandlers.ts`) calling `extract_source_from_svg`/
  `extract_source_from_pdf`.
- New `src/hooks/useJianpuWorkerImport.ts` (mirrors
  `useJianpuWorkerExports.ts`) exposing an `importFromFile(file: File)`
  function to components.
- New "Import" button placed next to `ExportControls` in the toolbar
  (wherever `<ExportControls .../>` is mounted in `AppWorkspace.tsx`/
  `AppHeader.tsx` — check at implementation time).
- On successful extraction: create a new file via the existing
  `useFileOperations.ts` create flow, pre-filled with the recovered source
  text, and open it in the editor. Decide on a sensible default filename
  (e.g. derived from the imported file's name, stripped of `.svg`/`.pdf` and
  given a `.jianpu` extension) — surface a rename prompt or just create with
  a default and let the user rename via existing rename UI, whichever is
  simpler given `useFileOperations.ts`'s existing API.
- On failure (no embedded source found — e.g. hand-edited or third-party
  file): show an error toast/notification using whatever toast/notification
  pattern the app already uses elsewhere (check for an existing toast
  component before introducing a new one).

### Testing

- e2e test (Playwright, per the existing `e2e/` suite pattern — see
  `e2e/import-shared-file-github.spec.ts` / `e2e/share.spec.ts` for style):
  export a file to SVG, then import that same SVG back in, assert the editor
  content matches the original source.
- e2e test for the failure path: import a plain/non-embedded SVG file,
  assert a graceful error is shown (not a crash).

## Explicitly out of scope

- Drag-and-drop import (start with a plain file picker button; drag-drop can
  be a follow-up if wanted).
- Importing MIDI/WAV (source embedding only makes sense for SVG/PDF, which
  are visual/print outputs meant to carry a hidden payload — MIDI/WAV have no
  natural place to hide it and are out of scope).

## Acceptance criteria

- [ ] `cargo run -- generate pdf simple.jianpu` produces a PDF from which the
      original source is recoverable via `extract_embedded_source`-equivalent
      logic (SVG-passthrough or XMP, per the Part A investigation).
- [ ] wasm-bindgen exposes extraction functions matching existing binding
      conventions in `crates/jianpu-wasm/src/`.
- [ ] Web editor has an Import button that round-trips: export SVG or PDF →
      import that file → editor shows the original source, verified by a
      Playwright e2e test.
- [ ] Graceful, non-crashing error UI when importing a file with no embedded
      source.
- [ ] `ARCHITECTURE.md` updated if the wasm-bindgen entry points or PDF
      generation layer's documented signatures change.
