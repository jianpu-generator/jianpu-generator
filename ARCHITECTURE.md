# Architecture

## Pipeline Overview

```
source (&str)
  → [parser]              → ParsedDocument
                             Raw event stream: notes, rests, chords, directives,
                             lyrics syllables per measure. No note measure grouping yet.
  → [grouper]             → Score
                             Notes grouped into measures; lyrics paired to each
                             measure's lyric slots (tie-aware);
                             parts organized into MultiPartMeasure slices;
                             optional `# sequence` section resolved into
                             Score.sequence spans.
  → [compiler]            → CompileResult
                             Logical grid: each note/rest assigned to a column,
                             underlines computed, slur spans recorded.
  → [consolidator]        → CompileResult
                             Mixed notes+lyrics rows split; duplicate rows with
                             identical content suppressed per measure.
  → [grid_layout]         → Vec<GridPage>
                             Grid elements placed into rows with heights and column
                             counts; rows wrapped across pages; slur arcs resolved
                             to same-system or cross-system variants.
  → [coordinate_resolver] → Vec<AbsolutePage>
                             Every element assigned absolute x/y coordinates in
                             points; grid geometry collapsed to flat element list.
  → [renderer]            → Vec<SvgDocument>
                             SVG primitives (Text, Line, Circle, Path) produced
                             for each absolute element.
  → [serializer]          → Vec<String>
                             SVG strings, one per page, ready to write to disk.
```

## Layer Details

### Parser
- Module: `src/parser/`
- Entry: `parser::parse(source: &str, filename: &str) -> Result<ParsedDocument, IrrecoverableError>`
- Key types: `ParsedDocument` (also carries `sequence: Option<SequenceSection>` and `sequence_parse_errors: Vec<RecoverableError>` from the optional `# sequence` section — see **Sequence resolution** in the glossary; also carries `group: Option<GroupSection>` and `group_parse_errors: Vec<RecoverableError>` from the optional `# groups` section; also carries `abbreviation_references: Vec<AbbreviationReference>` — every `[Abbrev]` key-prefix reference found in `# score`, in file order, each `{ abbreviation, span }` with `span` covering just the trimmed abbreviation text (excluding brackets/whitespace) — see **Rename-symbol support**), `ParsedTimedTrack`, `ParsedScore`, `ScoreEvent` (includes `PercussionHit(ParsedPercussionHit)`; `LabelChange(String)`'s `Spanned` wrapper carries a span narrowed to just the quoted label text, not the whole `label="..."` token), `ParsedNote` (carries `Accidental` for melody notes; tie intent via `tie_to_next_span: Option<Span>` with `tie_to_next()` accessor; also carries `tuplet: Option<TupletInfo>` — see **Tuplet** in the glossary), `ParsedRest`, `ParsedChordNote` (also carries `Accidental` and `tie_to_next_span`), `ParsedPercussionHit` (`ParsedNote` minus pitch/accidental — carries duration, dotted, group membership, tie/slur fields), `TupletInfo` (`{ num, den }` — see **Tuplet** in the glossary), `ParsedMetadata`, `JianPuPitch`, `Accidental` (`Sharp`/`Flat`/`Natural`; applies to both melody notes and chord notes), `Syllable`, `Soundfont` (vocal/piano/string; selects MIDI channel+program — on a `PartKind::Percussion` part, the number is instead a fixed GM percussion key rather than a GM program number, and is not validated against the melodic instrument catalog), `PartDecl` (carries `soundfont`, `volume`, `octave_offset`, `kind: PartKind`, `abbreviation_span: Span` — the abbreviation token's own byte span on its declaration line, used by rename-symbol — `PartKind::Percussion` reuses `&[ScoreLineRole::Notes]` for its score line roles), `SequenceSection` (parsed from `src/parser/sequence_parser.rs`'s `parse_sequence(content, offset) -> (Option<SequenceSection>, Vec<RecoverableError>)` — a comma-unzipped list of section-label references, each a `SequenceEntry { label, label_span, omit_parts, omit_part_spans, span }` where `omit_parts` comes from an optional `(-abbrev -abbrev ...)` suffix naming part/group abbreviations to omit from that occurrence's playback, e.g. `Chorus(-S -A2)`, and `label_span`/`omit_part_spans` are the byte spans of just the label text and each omitted abbreviation (used by rename-symbol) — see **Sequence resolution** in the glossary), `GroupSection`/`GroupDef` (parsed by `src/parser/group_parser.rs`'s `parse_group(content, offset) -> (Option<GroupSection>, Vec<RecoverableError>)` — carries `abbreviation_span`/`member_spans: Vec<Span>` alongside `abbreviation`/`members`, for rename-symbol — see **Group** in the glossary). `# groups` is parsed before `# score` so `group_parser::resolve_and_validate_groups(group_section, declarations) -> (Vec<ResolvedGroup>, Vec<RecoverableError>)` can run first; its `ResolvedGroup { abbreviation, members }` list (each member a concrete, transitively-resolved part abbreviation, all sharing one `PartKind`) is threaded into `score::interleaved_parser::parse(content, base_offset, declarations, resolved_groups) -> ParseResult` and on into `desugar::desugar_groups(groups, declarations, resolved_groups, base_offset)`, which lets a `[GroupAbbrev]` key prefix in `# score` broadcast a line to every resolved member — see **Group** in the glossary.

### Grouper
- Module: `src/grouper/`
- Entry: `grouper::group(doc: ParsedDocument) -> Result<Score, IrrecoverableError>`
- Key types: `Score` (carries `sequence: Option<Vec<SequenceSpan>>`, resolved by `resolve_sequence()` in `src/grouper/sequence_resolution.rs` — see **Sequence resolution** in the glossary), `SequenceSpan` (`label`, `start`, `end`, `omit_parts`, `omit_parts_display`: an inclusive resolved measure-index range for one `# sequence` entry, plus that occurrence's part abbreviations to omit from MIDI/WAV playback — `omit_parts` expands any group abbreviation in the entry's `(-abbrev ...)` suffix to its member parts (used for filtering), while `omit_parts_display` keeps a group abbreviation unexpanded (used for the "Sequence: ..." summary line, which shows the group's own label rather than its members) — see **Sequence resolution**), `MultiPartMeasure` (carries `bpm`/`key`/`time_signature`/`label` (all non-persisting on this type — see below) plus the always-resolved, persisting `merge_duplicate_measures_across_parts`/`hide_resting_parts` booleans), `PartRow` (Timed), `PartSlice` (carries `soundfont`, `volume`, `octave_offset`, `group_provenance: Option<String>` — the `[GroupAbbrev]` broadcast that produced this measure's content, when not overridden; see **Group** in the glossary — `resolution_multiplier: u32`, copied unchanged from the source `GroupedMeasure::resolution_multiplier`; see **Tuplet** — and `beat_group_size: u32`, copied unchanged from the source `GroupedMeasure::beat_group_size`), `Notes`, `NoteEvent` (includes `Percussion(GroupedPercussionHit)`), `GroupedNote`, `GroupedRest`, `GroupedChordNote` (`GroupedNote`/`GroupedChordNote` use `tie_to_next_span` + `tie_to_next()` accessor; all four `Grouped*` note types also carry `tuplet: Option<TupletInfo>`, copied through unchanged from the corresponding `Parsed*` field — see **Tuplet** in the glossary), `GroupedMeasure` (intermediate: notes + `paired_lyrics: Vec<Vec<Syllable>>` — one entry per verse, tie-paired against the notes independently per verse — plus `group_provenance: Option<String>` carried from `ParsedTimedTrack.per_measure_group_provenance`, `resolution_multiplier: u32` — see **Tuplet** — and `beat_group_size: u32`, the quarter-beat width of one beam group under the time signature in effect for that measure: `4` for simple meters, `6` for compound meters (6/8, 9/8, 12/8, ...), computed by `PartGrouper::beat_group_size` from the time signature tracked via `TimeSignatureChange` events and unscaled by `resolution_multiplier`). `PartSlice.lyrics: Vec<Lyrics>` carries the same one-entry-per-verse shape through to the compiler; a part's verse count is per-measure (see **Lyrics line**/**Verse** in the glossary).
- `src/tuplet.rs`'s `resolution_multiplier_of(events: &[Spanned<ScoreEvent>]) -> u32` / `apply_resolution_multiplier(events: Vec<Spanned<ScoreEvent>>, resolution_multiplier: u32) -> Vec<Spanned<ScoreEvent>>` is a stage-agnostic pair used by both the parser and the grouper (see **Tuplet** in the glossary for the parser-side use). On the grouper side, `part_grouper_group::group_timed_track` calls both once per measure (one `ParsedMeasureSlot::Real`'s event list), before that measure's events reach `PartGrouper`: `resolution_multiplier_of` scans for `TupletInfo` tags and computes `resolution_multiplier = lcm(every tagged event's num)`, then `apply_resolution_multiplier` multiplies every event's `duration` by it (plain notes too, so the measure's grid stays proportionally consistent) and further multiplies tuplet-tagged events by `den / num` (exact, since `resolution_multiplier` is a multiple of `num`). `PartGrouper::begin_measure_slot(resolution_multiplier)` (called once per `ParsedMeasureSlot::Real`, before its rescaled events are pushed) scales the capacity check (`PartGrouper::effective_capacity() = capacity * resolution_multiplier`) so a measure's flush boundary still lands correctly post-rescale; the multiplier resets back to `1` only once that measure actually flushes (`flush_measure`), since the accumulating measure isn't always flushed by the time all its events have been pushed (e.g. the score's trailing measure, flushed later by `finish`). `resolution_multiplier` defaults to `1` and the rescale is then a no-op, so non-tuplet music is unaffected. `midi::midi_notes::duration_to_ticks(quarter_beats, multiplier)` divides `multiplier` back out when converting a (possibly rescaled) duration to MIDI ticks; grid-column pixel width needs no equivalent division — see **Tuplet**.
- `merge_duplicate_measures_across_parts`/`hide_resting_parts` on `MultiPartMeasure` are resolved (not `Option`) by `DirectiveGrouper` (`src/grouper/directive_grouper.rs`): seeded from `Metadata::merge_duplicate_measures_across_parts`/`Metadata::hide_resting_parts` (the `# metadata` default) and overridden from a given measure onward by a `merge_duplicate_measures_across_parts=`/`hide_resting_parts=` directive line, persisting like `bpm`/`key`/`time` until the next override — unlike those three, they carry the fully resolved value on every measure rather than `Some` only where changed, since downstream consumers (`compiler::compile_measure`, `consolidator::consolidate_block`) need a plain value per call and have no rendering reason to know whether it just changed.

### Compiler
- Module: `src/compiler/`
- Entry: `compiler::compile(score: &Score) -> CompileResult`
- Key types: `CompileResult` (carries `tuplet_spans: Vec<TupletSpan>` alongside `slur_spans`, populated the same way — see below), `MeasureBlock` (carries `represents_measures: usize`, the number of original source measures the block stands in for — `1` normally, `> 1` when a rest run was folded; consumers that walk blocks and assume one block == one measure must advance their measure counter by this field, not by `1`; also carries `merge_duplicate_measures_across_parts: bool`, copied from the originating measure's `MultiPartMeasure::merge_duplicate_measures_across_parts` — see Consolidator below), `MeasureRow` (carries `group_provenance: Option<String>`, copied from the source part's `PartSlice.group_provenance`), `ColumnElement` (carries `note_id: Option<usize>` — see **Note identity** in the glossary), `ElementContent` (includes `PercussionHit`, threaded through `GridContent`/`PostArcGridContent`/`AbsoluteContent`/`SvgVariant::PercussionHit` and rendered centered via `render_percussion_hit`; also includes `MultiMeasureRest { count }`, threaded the same way through `GridContent`/`PostArcGridContent`/`AbsoluteContent`/`SvgVariant::MultiMeasureRest` and rendered via `render_multi_measure_rest` — see **Multi-measure rest** in the glossary), `SlurSpan`, `TupletSpan` (`{ part_index, measure_index, from_column, to_column, label }` — like `SlurSpan` but a single `measure_index` instead of `from_measure`/`to_measure`, since a tuplet never crosses a measure boundary; `label` is the tuplet's printed digit, e.g. `"3"` — see **Tuplet** in the glossary), `ArcKind`, `Decoration`
- `compiler::visible_part_indices(measure: &MultiPartMeasure) -> Vec<usize>` resolves which of `measure.parts` are actually compiled/sounded for that measure (an all-rest part is hidden when `hide_resting_parts` is in effect and at least one other part has real content). `compile_measure` uses it directly; `midi::timing::note_timings_seconds` (see **Note identity**) also walks `measure.parts` filtered through this same function, so its per-part `note_id` counters advance in lockstep with `ColumnElement::note_id`.
- `compile()`'s main loop still produces one block per source measure (preserving per-measure `cross_states`/`slur_spans`/bar-number bookkeeping); a post-pass `merge_rest_runs()` then folds maximal runs of 2+ eligible all-rest measures (see **Multi-measure rest**) into single blocks. Grid layout stays unaware of this folding — it only ever sees already-resolved blocks and lays out whatever `ElementContent`/`GridContent` variant it's given.
- `hide_resting_parts` (from `MultiPartMeasure::hide_resting_parts`, resolved per measure — see Grouper above) gates `compile_measure`'s omission of an all-rest part's row when at least one other part in the same measure has real content; when `false`, every part's row is rendered even if it's all rests.
- `PartSlice` also carries `resolution_multiplier: u32` (copied from the source `GroupedMeasure::resolution_multiplier` by `combiner::build_part_rows`; `1` for measures with no tuplets). `compiler::part_slice::compile_part_slice` reads it once per slice into `PartState::multiplier`, and every quarter-beat-grid literal in `part_slice.rs`/`part_slice_unit.rs` — the underline-count thresholds (base `1`/`2`/`3`), the note-dash spacing (base `4`) — is expressed as `BASE_CONST * multiplier` so a rescaled measure still lays out correctly. The beam-flush check itself (`beat_position % (beat_group_size * multiplier) == 0`) instead uses `PartState::beat_group_size`, read from `PartSlice::beat_group_size` — `4` for simple meters, `6` for compound meters — so a run of beamed notes/rests groups by dotted-quarter (3 eighth notes) rather than quarter-note in 6/8, 9/8, 12/8, etc. This is exact for untagged (non-tuplet) notes/rests in a rescaled measure, since their `duration` was scaled by exactly `multiplier` too; a tuplet-tagged unit's `duration` is additionally ratio-compressed (`* den / num` by `rescale_tuplets`), so before comparing against the underline-count thresholds, `compile_unit` first undoes that compression (`* num / den`, exact since `duration` was constructed as a multiple of `den`) to recover the note's written duration scaled by `multiplier` — so underline count reflects each note's written value (e.g. sixteenth notes get a double underline) independent of the tuplet's rescaled duration; the tuplet bracket/number is a separate overlay on top (see **Tuplet** in the glossary). `column: u32` itself needs no scaling — it's a pure additive grid index that already accumulates whatever (possibly rescaled) `duration` each unit was given.
- `TupletSpan`s are accumulated during the same pass as `SlurSpan`s, but by a separate, simpler mechanism (`compiler::tuplet_spans`'s `record_tuplet_tag`/`finish_tuplet_spans`, called from `compile_timed_unit`/`compile_unit` via the new `TimedUnit::tuplet()` trait method, and directly off `GroupedRest.tuplet` in `compile_rest`) since a tuplet never carries across measures: `PartState` holds one `current_tuplet: Option<PendingTupletSpan>`, reset fresh per `compile_part_slice` call, tracking the first/most-recent column of the contiguous run of notes/rests sharing one `TupletInfo` value; any break (an untagged event, or a different ratio) flushes it into `CompileResult.tuplet_spans`, remapped through `merge_rest_runs`'s `measure_to_block` exactly like `slur_spans`.
- A change in `merge_duplicate_measures_across_parts`/`hide_resting_parts` between two otherwise-collapsible measures forces a new run boundary in `merge_rest_runs()`, the same way a `label` does, since a merged block carries one resolved setting pair (taken from the run's first measure) for every measure it stands in for.

### Consolidator
- Module: `src/consolidator/`
- Entry: `consolidator::consolidate(result: CompileResult) -> CompileResult`
- Splits mixed `notes lyrics` rows into one notes row plus one lyrics row per verse (`ElementContent::Lyric { text, verse }` groups by `verse`), each verse's row getting a distinct `RowId` (`"{part}-lyrics-{verse}"`), then removes duplicate rows within each measure when their `elements` are identical (labels and ids are not compared). A standalone `lyrics`-part row (`ElementContent::LyricLine { text, verse }`, no notes) has no notes row to split off, so it only goes through the multi-verse split when it carries more than one verse. `slur_spans` are passed through unchanged.
- `merge_duplicate_measures_across_parts` (read per block from `MeasureBlock::merge_duplicate_measures_across_parts`, resolved per measure by the grouper — see Grouper above) gates only merges between rows with different `source_part_index`; rows from the same part still merge regardless.
- Because each verse gets its own `RowId`, a part's verse count changing between two measures changes that measure's row-id list, so `grid_layout::layout::pack_into_systems`'s existing row-identity check (see **System**) already forces a new system at that boundary — no separate verse-count check is needed.
- When rows merge, `merge_labels()` sets the surviving row's label to the shared group abbreviation when every merged row's `group_provenance` traces to the same `[GroupAbbrev]` broadcast (see **Group** in the glossary); otherwise it falls back to the space-joined concatenation of each source row's original label (its part abbreviation), and the surviving row's `group_provenance` is cleared to `None` so a later merge in the same pass can't mistake a partially-diverged cluster for a fully in-group one.

### Grid Layout
- Module: `src/grid_layout/`
- Entry: `grid_layout::layout(result: &CompileResult, config: &RenderConfig, header: &Header, width_pt: f32, height_pt: f32) -> Vec<GridPage>`
- Key types: `GridPage` (carries `playback_cursor_targets: Vec<PlaybackCursorTarget>`, `part_label_click_targets: Vec<PartLabelClickTarget>`, `lyric_click_targets: Vec<LyricClickTarget>`, `lyric_label_click_targets: Vec<LyricLabelClickTarget>`, and `bar_number_click_targets: Vec<BarNumberClickTarget>` alongside `measure_highlights`/`error_highlights`/`measure_click_targets` — see **Playback cursor**, **Part label click target**, **Lyric click target**, **Lyric label click target**, **Bar number click target**), `GridRow`, `GridElement`, `GridContent` (includes `TupletBracket { label }` — same-system-only counterpart of `TieOrSlur`, with no `Tail`/`Head` split since a tuplet never crosses a system — resolved by `grid_layout::tuplet_placement::resolve_tuplet_spans` from `CompileResult.tuplet_spans`, mirroring `slur_placement::resolve_slur_spans`; see **Tuplet** in the glossary), `HAlign`, `VAlign`, `ColumnGeometry`, `MeasureColumnLayout`, `PlaybackCursorTarget` (`row_start`/`row_end`/`column_start`/`column_end` like `MeasureHighlight`, plus `source_part_index`/`note_id`, plus `click_row_end` — the note's own click/selection target's bottom row, which (unlike `row_end`) never absorbs a following lyric verse row; see **Note click target**), `PartLabelClickTarget` (`row_start`/`row_end`/`source_part_index`/`measure_index_start`/`measure_index_end` — see **Part label click target**), `LyricClickTarget` (`row`, `column_start`, `column_end`, `source_part_index`, `note_id`, `verse` — a single row/column-span pair, unlike `PlaybackCursorTarget`'s `row_start`/`row_end`, since one syllable never spans more than one row — see **Lyric click target**), `LyricLabelClickTarget` (`row`, `source_part_index`, `verse`, `measure_index_start`, `measure_index_end` — a single row within the fixed-width label region, the lyric-side mirror of `PartLabelClickTarget` — see **Lyric label click target**)
- `grid_layout::system_walk::for_each_system(page_systems, tuplet_bracket_map, header, base, hide_system_dividers, visit)` is the shared page→system→row-offset walk behind every `compute_all_*` function below (and `compute_all_measure_click_targets` above): it threads `row_offset` across system-divider rows, decoration rows, and each system's own musical row count, invoking `visit(page_idx, system, row_offset, tuplet_part_indices, musical_row_count)` once per non-empty system. Any state a caller accumulates across systems (a running `global_measure_index`, an output `Vec`) it owns itself and mutates from inside the closure.
- `grid_layout::playback_cursor::compute_all_playback_cursor_targets` (walks `for_each_system`) groups each `MeasureRow`'s elements by `note_id` per block and emits one `PlaybackCursorTarget` per contiguous run, scoped to that one part's own sub-rows (`note_row_spans`) rather than the whole system's row range `MeasureHighlight` uses. A tied note split across a system/line break, or a repeated measure position with no navigation-aware remapping, can legitimately produce more than one `PlaybackCursorTarget` sharing the same `(source_part_index, note_id)` — the frontend highlights all of them together. `playback_cursor::note_row_spans` (renamed from `part_row_ranges`) returns one `NoteRowSpan { row_start, playback_row_end, click_row_end }` per row template: `playback_row_end` absorbs any immediately-following lyric verse row(s) (feeding `PlaybackCursorTarget::row_end`), while `click_row_end` is captured before that absorption and never extends past the note row's own sub-rows (feeding `PlaybackCursorTarget::click_row_end`) — see **Note click target**.
- `grid_layout::click_targets::compute_all_part_label_click_targets` walks `for_each_system`, reusing `playback_cursor::note_row_spans`' `playback_row_end` (not `click_row_end`) for each labeled note row's `row_end` — a part label is a shortcut for "select everything under this label," lyrics included, so (unlike a note's own click target) it deliberately absorbs any following lyric verse row(s) — and accumulating the same running `global_measure_index` to give every part label in a system its `measure_index_start`/`measure_index_end` — that system's full measure range (including merged multi-measure rests, via `MeasureBlock::represents_measures`). Skips rows `expand::expand_note_part` never draws a `RowLabel` for (an empty `label`, or a lyric/absorbed-verse row) so a click target only ever exists where the label itself is visibly drawn.
- `grid_layout::click_targets::compute_all_lyric_click_targets` walks `for_each_system`, but per-syllable rather than per-note: `lyric_row_absolute_indices` mirrors `note_row_spans`'s cursor walk except it records each verse row's own single absolute row index instead of merging it into its note row's combined span, since a `LyricClickTarget` (unlike a `PlaybackCursorTarget`) never needs to span more than one row. One target is emitted per `(source_part_index, note_id, verse)` triple actually present in that row's elements — see **Lyric click target**.
- `grid_layout::click_targets::compute_all_lyric_label_click_targets` walks `for_each_system`, reusing the same `lyric_row_absolute_indices` walk as `compute_all_lyric_click_targets` (rather than `note_row_spans`) to find each verse row's own absolute row index, and the same running `global_measure_index` accumulation as `compute_all_part_label_click_targets` to give every verse label in a system its `measure_index_start`/`measure_index_end`. One target is emitted per verse row with a non-empty `label` (`layout::lyric_row_verse` reads the row's own `verse` field, the same peek `expand::expand_lyric_part` uses to build its `RowLabel` text) — see **Lyric label click target**.
- `grid_layout::click_targets::compute_all_bar_number_click_targets` walks `for_each_system`, alongside the same `global_measure_index` accumulation `compute_all_measure_click_targets` performs. `MeasureClickTarget`'s row range never reaches into the shared directive row above the musical rows (`for_each_system` advances `row_offset` past it before `visit` runs), so a measure's own bar number — drawn there by `layout_decoration::make_decoration_row` — falls outside every existing click target; this is a second, narrower target (`row`/`column`, not a row/column *range*) sized to just that bar number's own grid column, one row up (`row_offset.saturating_sub(1)`). Emitted for exactly the blocks whose bar number `make_decoration_row` actually draws — `layout_decoration::directive_line_should_emit(index, dec)` (shared by both) — so an otherwise-plain mid-system measure's undrawn bar number gets no click target either. See **Bar number click target**.
- `layout::note_part_sub_row_heights(base) -> [f32; 7]` returns `[tuplet_bracket, arc, above_dot, note_head, below_dot, half_ul, quarter_ul]` — the tuplet-bracket row is reserved unconditionally for every note-part row (like the arc row already was), so it counts toward every fixed sub-row index/count derived from it: `expand::expand_note_part`'s `arc_sub`/`head_sub` (`(1, 3)` for a note row vs. `(0, 1)` for a chord-only row, which has no tuplet-bracket row and keeps the old 4-row `chord_part_sub_row_heights` layout), `highlight::system_musical_row_count`, and `playback_cursor::note_row_spans` (both `7` in place of the old `6` for a non-chord row). Because this row is unconditional, every note-part row is one sub-row taller than before Step 7 added it, even for a score with no tuplets at all — unlike Step 6's grid-width/MIDI-tick changes, this is *not* a pixel-identical no-op for existing (non-tuplet) content.
- `grid_layout::click_targets::targets_on_page<T: Clone>(targets: &[(usize, T)], page_idx: usize) -> Vec<T>` is the generic filter behind every `GridPage`-per-page split in `layout()` — measure/playback-cursor/part-label/lyric/lyric-label click targets alike — replacing four near-identical hand-copied `*_on_page` functions.
- `config.hide_system_dividers` (from `Metadata::hide_system_dividers`, `# metadata` field `hide_system_dividers`, default `no`) gates `layout::build_page_rows`'s insertion of the full-width `GridContent::HorizontalLine` separator row between systems, and the corresponding gap in `layout()`'s page-break height accounting; when `true`, no divider row or gap is inserted between systems.
- `GridRow.has_label_region` (`true` for system rows built by `expand::expand_system_to_rows`/`layout_decoration::make_decoration_row`, `false` for header/footer/separator rows) marks which rows reserve `LABEL_COLS` columns for the part label. `GridRow::column_geometry(usable_width_pt, label_width_pt) -> ColumnGeometry` uses this flag to give the label region a fixed pixel width (`config.part_label_width_pt`) independent of that row's own `column_count`, while the remaining columns still split the rest of the width evenly — this is what keeps the part-label column the same rendered width across systems of differing musical density, rather than the old uniform `usable_width_pt / column_count` division which made the label's width vary with each system's content.
- `GridRow.measure_layout: Vec<MeasureColumnLayout>` (one entry per measure in the row's system, shared by every row of that system — built once by `layout::build_measure_column_layout(system, config)` and threaded into `expand::expand_system_to_rows`/`layout_decoration::make_decoration_row`) records each measure's `start_col`, `col_count` (`block_column_width`), and `weight` (`layout_spacing::measure_note_weight`, the max summed real glyph width — measured via `font_metrics::monospace_char_advance_width`/`monospace_text_width` against `config`'s lyric font size, not a raw event count — of note/rest/percussion-hit/chord-symbol elements across the measure's part rows, so density scales with the busiest part rather than the part count; dashes and bar lines don't contribute here; a collapsed `MultiMeasureRest` gets a fixed weight of `MULTI_MEASURE_REST_WIDTH` instead). Per-column weights within a measure (`layout_spacing::measure_column_weights`, also `config`-aware) are likewise real font-metric widths for glyph columns (notehead/rest/chord/dash/lyric), while `BarLine`/`Underline`/`MultiMeasureRest` columns keep their old arbitrary flat weights (`THIN_MARK_WEIGHT`/`0.0`/a fixed per-column share) since they aren't glyphs with a measurable rendered width. `column_geometry` uses it to split the music region into one `ColumnSegment` per measure, sized by `MIN_MEASURE_WIDTH_PT` (a fixed floor) plus a share of the remaining width proportional to `weight` — so denser measures render wider and sparser ones narrower, while columns within one measure stay uniform. When `measure_layout` is empty (headers/footers/separators, or a row with no system), `column_geometry` falls back to the old single-scalar uniform division. Because `x_start`/`col_width` become piecewise-linear across segments, span-width consumers (`coordinate_resolver::resolve`'s arc/underline formulas, `coordinate_resolver::highlights`'s highlight/click-box formulas) must compute a span's width as `x_start(end) - x_start(start)` rather than `col_width(start) * span`, so a span crossing measures of different width still gets its true pixel extent. `ColumnGeometry::glyph_left_anchor_x(col, padding) -> f32` (`x_start(col) + padding`) is the shared helper for note/rest/dash/chord/percussion-hit/lyric-syllable anchoring and arc/underline/tuplet-bracket endpoints: every glyph anchors at the column's left edge plus `padding`, the same regardless of the column's own width or what else shares it — replacing an earlier weighted-centering formula that scaled a glyph's anchor toward the column's true center in proportion to its own weight share of the column's total, which made two visually similar notes land at different offsets depending on what else shared their column. `padding` itself is no longer one flat constant: every flush-left renderer (note head, rest, percussion hit, chord symbol, note dash, lyric syllable) now draws `TextAnchor::Start` at this anchor, so `coordinate_resolver::resolve::flush_left_padding` computes `padding = GLYPH_LEFT_PADDING - bearing(leading_char)` per element — the leading character's own left-side bearing (`font_metrics::monospace_glyph_left_bearing`/`cjk_glyph_left_bearing`, measured against the pinned font actually used to render that content type) — so every glyph's *ink*-left-edge, not just its anchor, lines up flush regardless of which content type shares the column (see `font_metrics::is_cjk_char`/`lyric_font_size`, the shared CJK-detection/font-size-selection helpers behind the lyric case). The tie/slur/underline/tuplet-bracket span markings in `resolve_span_marking` still use one flat `padding` (`GLYPH_LEFT_PADDING + note_number_width * 0.5`, approximating a note's *center* rather than any one glyph's bearing, since a span can cover notes of differing pitches/widths) — the same nominal `note_number_width` box the renderer's own `center` reconstructs in `glyph_renderers.rs::render_note_head` for its accidental/dot placement.

- `renderer::new_renderer::glyph_renderers::render_tuplet_bracket` (dispatched alongside `render_tie_or_slur` in `new_renderer.rs`) draws a flat bracket — two short downward `SvgKind::Line` ticks joined by a horizontal `SvgKind::Line` spanning `width`, with an `SvgKind::Text` label (the tuplet digit) centered above the midpoint — visually distinct from `render_tie_or_slur`'s curved `SvgKind::Path` arc, so a tuplet bracket and a slur/tie arc stacked in the same measure (bracket row above arc row — see **Grid Layout**) don't look identical.

- `config.directive_row_offset` (from `Metadata::directive_row_offset`, `# metadata` field `directive_row_offset`, an `Offset { x, y }` in points, default `(0, 0)`) is applied unconditionally by `render_directive_line` (`src/renderer/new_renderer/directive_line.rs`) to every directive row — the bar-number/section-label/key/bpm/time-signature line above the staff — shifting all of that row's elements (bar-number text, key/bpm/time-signature text, optional label background rect, optional independent label text) together, after `coordinate_resolver` has already resolved their absolute position. `AbsoluteContent::DirectiveLine` renders the bar number, section label, and the key/bpm/time-signature run as three independently-positioned elements rather than one shared text run, each with its x position precomputed in `coordinate_resolver::content_conversion` from real glyph-advance measurements (`src/font_metrics.rs`, pinned against the same font used for PDF export — embedded via `include_bytes!` on the host CLI build, or supplied at runtime via `set_directive_line_font_bytes`/`set_monospace_font_bytes` on the `wasm32` build, since embedding both fonts in the wasm binary would otherwise add ~16MB to it) instead of a character-bucket heuristic: `bar_number: Option<TextSpan>` is pinned to the line's start (offset 0); `label_x_offset: f32` positions the section label past the bar number (plus a fixed gap) when one precedes it, zero otherwise; `spans_x_offset: f32` positions the remaining spans past whichever of `bar_number`/`label` is present, so none of the three overlap regardless of their measured widths. When a label is present, its `<g data-tag="section-label">` group also carries an invisible `SectionLabelClickTarget` rect spanning the whole directive line (bar number through trailing spans) as its first child — without it, the group's actual clickable area would be only the union of its children's painted pixels, which leaves an unpainted gap (and therefore a dead click zone, despite `cursor: pointer` covering it) whenever a directive line has a label but no trailing spans (e.g. a bare `label="B"` line). The `# sequence` summary header line renders through the same function but is explicitly excluded (`AbsoluteContent::DirectiveLine.apply_row_offset = false`). It never reaches `grid_layout` or `coordinate_resolver` — those layers are unaware of it.

## Glossary

| Term | Definition |
|------|-----------|
| **System** | A horizontal row of measures that fit on one line of a page. The grid layout wraps measures into systems based on column count and page width. |
| **Measure** | One bar of music. The score is a flat sequence of `MultiPartMeasure`s. |
| **Part** | A single instrument or voice track (e.g. soprano, bass). Declared in `[parts]`. |
| **Part Slice** | One part's notes and lyrics (one or more verses) for a single measure (`PartSlice`). |
| **Timed unit** | The compiler-stage trait (`TimedUnit`, `src/compiler/timed_unit.rs`) unifying `GroupedNote`, `GroupedChordNote`, and `GroupedPercussionHit` — anything that occupies a duration in the grid and exposes `duration`/`dotted`/`double_dotted`/`group_membership`/`group_continuation`/`slur_key`/`tie_to_next`/`tuplet`/`element_content()`. Used as shorthand in conversation/docs for "note, chord, or percussion hit" collectively, since all three compile through the same grid-column machinery. |
| **Ditto** | A measure where every input line was `"`, meaning it repeats the previous measure. Rendered as blank; audio output still uses the resolved content. |
| **Column** | A logical horizontal slot in the compiler's grid. Each beat occupies one or more columns. |
| **Quarter-beat** | The smallest time unit used for duration arithmetic. A standard quarter note = 4 quarter-beats. |
| **Underline** | A horizontal line drawn below note heads to indicate duration subdivision. `level=0` = half-beat, `level=1` = quarter-beat. |
| **Octave Dot** | A dot drawn above or below a note head to shift its octave. Count = `octave.abs()`. |
| **Note Dash** | A visual `-` drawn after a note head for each extra beat of duration. |
| **Lyrics line** | One plain-text line per measure per `notes lyrics` part, tokenised into syllables and stored per measure (not as a global pool). Consecutive lyrics lines after the notes line are separate verses — see **Verse**. |
| **Verse** | One of a `notes+lyrics` part's lyric lines for a measure, 0-indexed. The number of verses is per-measure (declared implicitly by how many consecutive `[Part]` lyric lines follow the notes line) and can differ between measures for the same part; each verse is tie-paired against the notes independently and rendered as its own row. A verse-count change between two measures of the same part forces a system break (see **System**). |
| **Standalone lyrics part** | A `PartKind::Lyrics` part (`lyrics` kind): lyrics-only and adurational — no notes, so nothing to tie syllables to. Every `[Abbrev]` line is a full verse (`ElementContent::LyricLine { text, verse }`, one element per verse, tokenized syllables rejoined with spaces rather than tied one-per-note). Rendered as a single left-aligned text block via `GridElement::column_span` spanning the whole measure's column width, competing for the measure's pixel *width* (see `layout_spacing::measure_note_weight`'s `LyricLine` arm) without ever affecting its column *count*. |
| **Arc Span** | The full logical extent of one slur or tie arc, possibly crossing measure or system boundaries (`SlurSpan`). Carries `ArcKind` to distinguish ties from slurs. |
| **ArcKind** | Discriminant on `SlurSpan`: `Slur` (from `(…)` groups) or `Tie` (from `~`). Both render as arcs; the kind is available for future visual distinction. |
| **Decoration** | Measure-level metadata attached to a `MeasureBlock`: BPM, time signature, section label, bar number. |
| **Row Label** | The part name displayed at the left margin of a system row, in a fixed-width column (`Metadata::part_label_width_pt`, `# metadata` field `part_label_width_pt`, default `40` points) shared by every system in the score regardless of that system's musical density — see **Grid Layout**'s `ColumnGeometry`. A verse row (`expand::expand_lyric_part`) gets its own `RowLabel` too, in the same column: `"{part abbreviation}:v{1-based verse}"` (e.g. `"M:v1"`, `"M:v2"`), read from the verse row's own `label`/`ElementContent::Lyric.verse` — see **Lyric label click target**. |
| **RowId** | A unique string identifier for a compiler row, used to correlate rows across layout stages. |
| **Measure Start Time** | The elapsed-seconds offset of a measure boundary within a score's audio rendering, computed from cumulative MIDI ticks and any BPM changes (`midi::measure_start_times_seconds`). No longer drives any UI feature; `measure_start_times_seconds`/`measure_start_times_from_source` are used only for playback-order measure-boundary math (e.g. computing a playback-order offset in the `note_highlight_identity` test) — see **Playback cursor** for the mechanism that actually highlights playback position in the UI today. |
| **Playback cursor** | The discrete red highlight/rect drawn over whichever note/rest is currently sounding during playback, jumping note-to-note rather than gliding continuously (unlike a "playhead"/"playback line"). Rendered as `SvgKind::PlaybackCursorRect` (see **Renderer**), resolved from `AbsoluteContent::PlaybackCursorTarget` (see **Coordinate Resolver**), sourced from `GridPage.playback_cursor_targets: Vec<PlaybackCursorTarget>` (see **Grid Layout**). Driven on the frontend by `components/usePlaybackCursor.ts`'s `usePlaybackCursor` hook, which binary-searches each part's sorted note timings (`components/playbackCursorPosition.ts`) to find the active note at the current `<audio>` `currentTime` and toggles that note's rect's `fill` — see **Note identity** for how a note's timing is computed and matched to its rendered element. |
| **Note identity** | `(source_part_index, note_id)`: the identity key shared by a written note/rest's `ColumnElement`/`GridElement`/rendered `data-tag="note"` group and its MIDI/WAV timing, so the SVG preview can highlight whichever note is currently sounding, independently per part. `source_part_index` is the same raw `measure.parts` index `MeasureRow::source_part_index` already uses. `note_id` is a running counter per part, incrementing once per `NoteEvent` consumed from that part's `notes.events` — assigned by the compiler (`compiler::part_slice`, threaded per-part across measures via `PartCrossState::next_note_id`) when building `ColumnElement`s, and independently re-derived by `midi::timing::note_timings_seconds(score: &Score) -> Result<Vec<NoteTiming>, IrrecoverableError>` (`NoteTiming { source_part_index, note_id, start_s, end_s }`) when computing MIDI-tick-based timings — both walk `score.measures[i].parts[j].notes.events` in the same raw order (via `compiler::visible_part_indices`), independent of the MIDI writer's channel-pooling (`parts_matching`/`part_index_to_midi_channel`), so the two assignments agree. A tie continuation (`tie_to_next()`) reuses the id of the note it continues from, on both sides, rather than allocating a fresh one — mirroring the MIDI writer's own merge of a tied note into a single NoteOn/NoteOff pair — so a tie crossing a measure or system boundary is one `note_id` with one merged `NoteTiming` (extended `end_s`) but can still resolve to more than one `PlaybackCursorTarget` (see **Grid Layout**) if it crosses a line break. `audio_source::note_timings_from_source` (the `lib.rs`-level entry point, exported as WASM `list_note_timings`) deliberately does **not** run the score through **Navigation expansion** first, unlike `measure_start_times_from_source`: doing so would reassign `note_id`s along the expanded/repeated timeline instead of the written one. This makes no difference for a score with no `# sequence` section (expansion is then a no-op); for one that repeats, note highlighting is only accurate through the first pass. The frontend (`components/playbackCursorPosition.ts`, `components/usePlaybackCursor.ts`) binary-searches each part's sorted `NoteTiming`s to find the active note at the current playback time and toggles the `fill` of that `(source_part_index, note_id)`'s `PlaybackCursorRect`(s) (see **Renderer**) — see **Playback cursor**. `midi::timing::note_timings_seconds_for_range(score: &Score, start_pos: usize, end_pos: usize) -> Result<Vec<NoteTiming>, IrrecoverableError>` is the range-scoped counterpart backing `audio_source::note_timings_for_range_from_source`/WASM `list_note_timings_for_range`, used when playing a clip via `write_wav_for_measure_range_from_source` (e.g. "play from this measure") instead of the whole score: `start_s`/`end_s` are rebased to the *clip*'s own start (matching `measure_start_times_seconds_for_range`), but `note_id`s are still resolved via `build_written_note_id_lookup`/`compile(score).blocks` computed once over the passed-in `score`, which callers must pass as the *original, unexpanded* written score (unlike `measure_start_times_seconds_for_range`, whose `score` parameter is already the expanded score) — `note_timings_seconds_for_range` re-derives the expanded/playback-order timeline itself via `expand_navigation_with_note_positions` so `start_pos`/`end_pos` (already-resolved playback positions, not raw written indices — see **Navigation expansion**) line up with both the tick/tempo accounting and the written-score `note_id`s. |
| **Note click target** | A transparent, clickable/draggable hit rect layered over each rendered note/rest, distinct from the **Playback cursor**'s `PlaybackCursorRect`: that rect is `pointer-events: none` (its `fill` is owned exclusively by `usePlaybackCursor.ts` for playback highlighting), so a click on a note would otherwise fall through to whatever's beneath it (today, the enclosing measure's click target). Rendered as `SvgKind::TransparentRect { role: TransparentRectRole::NoteClickTarget }` (see **Renderer**), resolved from `AbsoluteContent::NoteClickTarget` by `coordinate_resolver::highlights::resolve_note_click_target` (see **Coordinate Resolver**) — sharing the same column-bounds math and `grid_layout::types::PlaybackCursorTarget` input as `resolve_playback_cursor_target`, but stopping its row range at `target.click_row_end` rather than `target.row_end`: a note's own click/selection target never extends down into a following lyric verse row (a lyric syllable is independently selectable via its own **Lyric click target**), unlike the playback-cursor rect, which does extend to visually cover the lyric text sounding with the note. It's emitted into its own sibling `Tag::Note` group rather than the playback rect's group, and resolved after it so it stays topmost for `elementFromPoint` hit-testing. Its `(source_part_index, note_id)` (see **Note identity**) round-trips to source text via `note_spans::list_note_spans_from_source(source: &str, filename: &str) -> Result<NoteSpansResult, IrrecoverableError>` (`NoteSpansResult { spans: Vec<NoteSourceSpan> }`, `NoteSourceSpan { source_part_index, note_id, measure_index, start: Option<usize>, end: Option<usize> }`), exported as WASM `list_note_spans`. Ids are assigned by re-walking `Score.measures[i].parts[j].notes.events` with the same per-part running counter and tie-continuation reuse compiler::part_slice uses when building `ColumnElement::note_id` (see **Note identity**), so a `NoteSourceSpan`'s id always matches the `data-note-id` on the rendered group it maps back to. A rest has no single source token to anchor to, so its span's `start`/`end` are `None`. ## Web integration

The React app (`web/`) runs the compiler in a dedicated worker (`web/src/worker/jianpu.worker.ts`) backed by the `jianpu-wasm` crate. The main thread sends source text and asset bytes; the worker calls WASM exports and posts structured results back.

### Storage abstraction

- Module: `web/src/storage/`
- Key types: `StorageBackend` (`web/src/storage/types.ts`) — the interface both the browser-`localStorage` backend and a future GitHub backend implement; `FileStoreState` (`web/src/fileStore.ts`) remains the canonical in-memory shape used by every backend. `StorageBackend.load`/`createFile`/`duplicateFile`/`renameFile`/`deleteFile`/`restoreFile`/`saveContent` are async (to accommodate network-backed backends); `updateActiveContent` is sync with no persistence side effect. `saveContent` is the explicit call that persists the active file's content — debounce ownership lives in the hook layer, not the backend.
- `web/src/storage/localBackend.ts` — the only `StorageBackend` implementation so far. Thin async adapter over `fileStore.ts`'s pure, synchronous functions (`createFile`, `duplicateFile`, `renameFile`, `deleteFile`, `restoreFile`, `updateActiveContent`). Its `saveContent` is a no-op since `useLocalStorage` already persists on every state change.
- `web/src/storage/githubBackend.ts` — `GithubBackend` (extends `StorageBackend`), backed by GitHub's Contents API via `Octokit`. Config (`GithubBackendConfig`): `token`, `owner`, `repo` (always the fixed `jianpu-generator-storage`, see below), optional `branch`. Files always live under the fixed `scores/` top-level folder, with deleted files moved to a sibling top-level `trash/` folder, so further top-level siblings (e.g. `metadata`) can be added without a folder picker. No sha cache (refetches immediately before each write); rename/delete/restore are two sequential Contents API calls, not one atomic commit. Exposes a non-interface `lastError(): GithubBackendError | null` (`'conflict' | 'rate-limited' | 'network' | 'unknown'`) so the settings UI can render specific banners/prompts beyond the shared `SaveStatus`.
- `web/src/storage/githubAuth.ts` — OAuth device-flow auth, via `@octokit/auth-oauth-device` with a minimal duck-typed `request` stub that routes only the two CORS-blocked device-flow calls (`POST /login/device/code`, `POST /login/oauth/access_token`) through the Cloudflare proxy (see below); everything else (Contents API, `/user`, `/repos/...`) is called directly against `api.github.com`. `connectWithDeviceFlow(options)` runs the flow to completion and persists the token; `checkGithubAuthStatus()` validates a stored token against `GET /user`; `readStoredGithubAuth()`/`clearStoredGithubAuth()` are imperative accessors (for non-component callers) and `useGithubAuthToken()` is the reactive hook equivalent (for the settings UI). Disconnecting only clears the local token — it does not revoke it on GitHub's side.
- Entry: `useStorageBackend()` in `web/src/hooks/useStorageBackend.ts` — holds the `FileStoreState` in React state and exposes `store`/`setStore`/`backend`/`saveStatus`/`preference`/`switchBackend()`/`forceSave()`/`flushPendingSave()`. `local`'s state lives in `useLocalStorage` (seeded synchronously through `localBackend`'s local-only read helpers); `github`'s state is fetched via `backend.load()` into a plain `useState` whenever the backend identity (kind/owner/token) changes. Callers `await backend.xxxFile(store)` for structural operations (create/duplicate/rename/delete/restore — hit the backend immediately), then `setStore` the result; content edits go through the existing `setStore`/`backend.updateActiveContent` path and are separately debounced (`AUTOSAVE_DEBOUNCE_MS`, ~20s, via `use-debounce`'s `useDebouncedCallback`) into a `backend.saveContent()` call — one shared cadence for both backends, immaterial for `local` (no-op `saveContent`), kept low-frequency for `github`. `switchBackend(target)` persists the choice under `jianpu:storage-backend:v1` (`{ backend, github?: { owner } }`), force-flushing (and awaiting) any pending GitHub save first, and always lands on the demo file — there is no per-backend "last active file" memory. `flushPendingSave()` similarly force-flushes a pending GitHub save without cancelling the debounce timer or switching backend; `App.tsx`'s `handleSelect` calls it before changing the active file tab, since `shouldScheduleAutosave` deliberately does not schedule a new save on such switches.
- `web/src/components/StorageSettingsModal.tsx` — the settings UI that makes the GitHub backend reachable: a Radix Dialog offering "This browser" vs. "GitHub repository", an inline device-flow connect step (rendering `githubAuth.ts`'s `onVerification` `user_code`/`verification_uri`) when GitHub is selected but not connected, and, once connected, `@username` / repo-in-use (`<repo>/scores`) / "Disconnect". Repo selection is fully automatic: `ensureStorageRepo(octokit, owner)` (exported from this file) calls `octokit.rest.repos.get()` for the fixed `jianpu-generator-storage` repo name and creates it (private) on `404` — no picker, no confirmation prompt. Also renders `githubBackend.ts`'s `lastError()` as a rate-limit/offline banner, and resolves `409` conflicts via `resolveGithubConflict()` (also exported), a minimal "overwrite mine" (retry `saveContent`) vs. "discard mine" (`backend.load()` then `updateActiveContent` with the remote content) choice — no 3-way merge. `FileList.tsx`'s `FileTabBar` exposes the entry point (a "Storage…" button plus a saving/saved/offline status badge, `onOpenStorageSettings`/`saveStatus` props); `App.tsx` owns the modal's open state and threads `backend`/`preference`/`switchBackend`/`saveStatus` from `useStorageBackend()` down to both.
- **`cf-oauth-proxy/`** — a separate Cloudflare Pages Functions project, **not** part of `web/`'s build (Vite/pnpm never sees it; it's deployed as its own Cloudflare Pages project per `cf-oauth-proxy/README.md`). It exists solely to relay the two GitHub OAuth device-flow calls that don't send CORS headers (`POST /login/device/code` → `/device/code`, `POST /login/oauth/access_token` → `/oauth/token`), injecting the OAuth App's client secret server-side; every other GitHub API call the app makes goes straight from the browser to `api.github.com`. `web/`'s build points at a deployed instance of it via the `VITE_GITHUB_OAUTH_PROXY_URL` env var (set in `.github/workflows/pages.yml`); there is no revoke/disconnect endpoint in v1.

### Source editing

- Module: `src/source_edit/`
- Entries: `source_edit::update_part_declaration(source, abbreviation, new_mode, new_soundfont, new_volume, new_octave_offset) -> Option<String>`; `source_edit::shift_part_octave(source, abbreviation, delta: i8) -> String`
- `update_part_declaration` rewrites a single `# parts` declaration line in place (mode, optional quoted soundfont, optional volume `%`, optional octave offset). Used by the Edit Parts modal instead of any TypeScript parser.
- `shift_part_octave` bulk-rewrites the `'`/`,` octave marker on every `ScoreEvent::Note` belonging to one part in `# score` (the "notation octave" control in the web editor — distinct from `update_part_declaration`'s MIDI-only `octave_offset`, which never touches rendered notation). Parses via `parser::parse` to read each note's resolved `octave: i8` and full-token `Span` (`ParsedTimedTrack::measure_slots`), then splices new marker text into the raw source back-to-front by span. Measures where `per_measure_group_provenance[i]` is `Some(_)` (this measure's content came from a `[GroupAbbrev]` broadcast the part didn't override, so the source text is shared with sibling parts) are skipped entirely, never partially rewritten. Infallible / best-effort, mirroring `update_part_declaration`'s "not found → unchanged" convention: an unknown abbreviation, a `follow[X]` part (no notes of its own), `delta == 0`, or a parse failure all return `source` unchanged. No clamping on the resulting octave.

### Split-track export

- Module: `src/split_track.rs`
- Entries: `write_split_pdfs_from_source(source, filename, base_name, tracks_filter, fonts) -> Result<Vec<SplitPdfEntry>, IrrecoverableError>` (`pdf` feature); `write_split_midis_from_source(source, filename, base_name, tracks_filter) -> Result<Vec<SplitFileEntry>, IrrecoverableError>` (`midi` feature); `write_split_wavs_from_source(source, filename, base_name, tracks_filter, sf2_bytes) -> Result<Vec<SplitFileEntry>, IrrecoverableError>` (`wav` feature)
- Each parses/compiles the source once, then renders/synthesizes one output per track (`tracks_filter` empty → all score tracks).
- Key types: `SplitPdfEntry` (`track_name`, `filename`, `pdf`), `SplitFileEntry` (`track_name`, `filename`, `bytes` — shared by the MIDI and WAV variants)
- `zip_split_pdfs(entries: &[SplitPdfEntry])` / `zip_split_entries(entries: &[SplitFileEntry])` archive the entries into a single ZIP (`Vec<u8>`), one file per track named via `split_track_filename`.
- `src/lib.rs`'s `write_midi_from_source_filtered(source, filename, enabled_tracks, instruments) -> Result<Vec<u8>, IrrecoverableError>` (`midi` feature) is the whole-score counterpart used by `generate_midi`, mirroring `write_pdf_from_source_filtered` and `write_wav_for_measure_range_from_source`.

### Part declarations (source-level)

- Module: `src/part_info.rs` (re-exported from `src/lib.rs`)
- Entry: `list_part_declarations_from_source(source, filename, instruments) -> Result<Vec<SourcePartDeclaration>, IrrecoverableError>`
- Backed by `parts_parser::collect_source_raw_declarations()` — returns **raw** fields from each declaration line (before `follow[X]` inheritance). The Edit Parts modal displays these values.

### Rename-symbol support (source-level)

- Module: `src/symbols.rs` (re-exported from `src/lib.rs`)
- Entries: `collect_symbols(document: &ParsedDocument) -> Vec<Symbol>`; `rename_edits(document: &ParsedDocument, kind: SymbolKind, old_name: &str, new_name: &str) -> Vec<TextEdit>`
- Key types: `SymbolKind` (`Abbreviation` — parts and groups share one namespace, so both kinds of declaration collect under it — or `SectionLabel`), `Symbol { name, kind, occurrences: Vec<SymbolOccurrence> }`, `SymbolOccurrence { span, role: OccurrenceRole }` (`Declaration` or `Reference`), `TextEdit { span, replacement }`
- Built entirely on spans `ParsedDocument` already tracks (see **Rename-symbol support** in the glossary for which fields) rather than a separate parse pass; `rename_edits` is `collect_symbols` plus a lookup and a flat map from occurrence to replacement text, so it never mutates source itself — callers apply the edits.

### Score formatting (source-level)

- Module: `src/format_source.rs` (re-exported from `src/lib.rs`)
- Entry: `format_score(source: &str) -> String`
- A normal-editor toolbar action: per `# score` measure group, drops `[Key]` data lines that are entirely redundant with implicit-fill (an all-rest line for a `Notes`/`Chord`-role occurrence, an all-`_` line for a `Lyrics`-role occurrence), and collapses whitespace to single spaces on every surviving directive/data line. A key's droppable lines must be a *trailing* run (dropping an earlier verse out from under a later one with real content would shift it into the wrong slot) and dropping is blocked outright if it would leave the group with zero data lines (a parse error). `follow[X]` parts are excluded entirely (an explicit rest there is real content, not filler); `[GroupAbbrev]` broadcast lines are classified by their first resolved member's `PartKind` (`resolve_and_validate_groups` guarantees uniform kind across members) and otherwise treated like a plain part line.
- Classification/removability is hand-rolled directly from each key's raw per-group line count (mirrors `desugar::roles_for_group`'s static-kind branch without invoking it), and the output is spliced together directly from the filtered/normalized raw lines. `desugar::desugar_groups` is still run once over the filtered groups as a best-effort validity check (falling back to `source` unchanged on `Err`), but its materialized output is discarded. Real implicit-fill for the dropped lines happens later, ordinarily, whenever the resulting `.jianpu` source is actually parsed — exactly as it already does for any measure group that omits a part's line.
- Infallible / best-effort, mirroring `source_edit::update_part_declaration`'s "not found → unchanged" convention: a missing/empty `# parts` or `# score` section, or an internal parse failure, returns `source` unchanged.

`generate_pdf`/`generate_split_pdfs` (`pdf` feature) follow the same pattern as the MIDI/WAV exports above: structured `{ status, ... }` envelope, `Vec<u8>` font/soundfont parameters supplied by the caller rather than embedded in the WASM binary.

`web/src/shareUrl.ts` calls `compress_share_payload`/`decompress_share_payload` directly from the main thread (a separate WASM instance from the render worker's), lazily `init()`-ing on first use, to build/parse `#share=<base64url>` links. `decodeShareHashSuffix` falls back to the legacy `lz-string`-encoded format, then plain-JSON, for links created before this switch. `web/src/hooks/useNoteSelection.ts` calls `group_note_selection` the same way, on every note drag-select and editor-selection-change tick; it needs no debounce, since it's pure grouping over the already-fetched `note_spans` array rather than a re-parse of `source`. `web/src/hooks/useLyricSelection.ts` is the fully independent lyric-syllable counterpart, calling `group_lyric_selection` over a separately-fetched `lyric_spans` array — it shares no state with `useNoteSelection`, only the same unified mousedown/mousemove/mouseup gesture plumbing in `usePreviewDragSelection.ts` (see **Lyric click target**). Both wrap the same low-level `web/src/hooks/useByteRangeSelectionCore.ts`'s `useByteRangeSelectionCore<Cell, Span, Run>` for their shared plumbing — `selectedCells`/`runs` state, the `suppressNextEditorSelectionSyncRef` echo-guard, and the drag-select ⇄ Monaco-selection round-trip (`handleRangeSelect`/`handleEditorSelectionChange`) — each supplying its own grouping function, cell/span shape, and (for `useNoteSelection` only) an `onNoMountedEditor` fallback for Live/shared views; `useNoteSelection` layers `selectedNoteRangePlaybackInfo` on top of the core's `runs` via its own `useMemo`. The core is deliberately not itself a merge point between the two hooks — each still calls it independently, so a lyric selection can never leak into note-highlight state or vice versa.

The worker (`web/src/worker/jianpu.worker.ts`) gates its `render`/`renderWithHighlightRange` handlers on `ensureCoreFontsApplied()`, which awaits both wasm init and the SC+mono font bytes (resolved from the `loadPdfFonts` message the app already sends at boot — see `web/src/hooks/useFontsLoader.ts`) before calling `set_layout_fonts`; other handlers that don't reach the layout/render chain (`listParts`, `updatePartDeclaration`, `listMeasureSpans`, export handlers) aren't gated on it.

Worker messages: `listParts` → `{ parts, declarations }`; `updatePartDeclaration` → `{ source, declarations }` (hook updates `partDeclarations` immediately, without waiting for the debounced re-render); `importFromFile { bytes, kind: 'svg' | 'pdf' }` → `importOk { source }` / `importErr` (`web/src/worker/importMessageHandlers.ts` calls `extract_source_from_svg`/`extract_source_from_pdf`; `useJianpuWorkerImport.ts`'s `importFromFile(file: File) -> Promise<string>` is the promise-based wrapper `App.tsx`'s Import button uses, resolved/rejected from `useJianpuWorkerMessageHandler.ts`'s `pendingImportsRef` map keyed by request id, mirroring `updatePartDeclaration`'s pending-map pattern).
