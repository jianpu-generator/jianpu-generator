# TODO: rename the app to Poentaro (`poentaro.pages.dev`)

Progress tracker for the rename. Keep it updated as steps land, so the work
survives context compression. Branch: `feat/rename-to-poentaro`.

## Decisions (already agreed with the user)

- New name: **Poentaro** (Esperanto *poento* "point" + *-aro* "collection" =
  a points tally, so "score"; English pun on musical score; Esperanto is the
  anti-Babel language, which is the app's "one score, every notation" story).
- New home: `https://poentaro.pages.dev` (new Cloudflare Pages project
  `poentaro`; Pages projects can't be renamed).
- Old links must keep working via auto-redirect, **including** path, `?query`
  and `#hash` (share links carry payloads in both: `web/src/shareUrl.ts`,
  `web/src/syncedShareUrl.ts`, `web/src/urlFileParam.ts`).
- A plain 301 / Bulk Redirect is NOT enough: local files
  (`jianpu:files:v1`), the session (`jianpu:account-auth:v2`) and UI prefs
  live in origin-scoped `localStorage`. The old origin must hand them over.
- Handoff goes through a one-time worker endpoint (not the URL fragment,
  which can hit browser URL-length limits for large file stores).
- Keep internal names unchanged: `jianpu:` storage keys, worker name
  `jianpu-live-share-worker-rs`, D1 `jianpu-live-share`, crate names.
  (Superseded by step 8: everything meaning the app is renamed, except
  cloud resources that can't be renamed.)
- Cloudflare dashboard / production actions (create `poentaro` project, first
  deploy, switching the old project to the bridge) need the user's approval.

## Findings (from exploring the code)

- Saved browser data: `localStorage` keys all start with `jianpu:`
  (`files:v1`, `source:v5` legacy, `account-auth:v2`, `storage-backend:v1`,
  `part-toggles:v1`, `file-tree-expanded:v1`, `part-stream-diff-layout:v1`,
  `preview-notation:v1`), PLUS the cloud outbox in IndexedDB: one database
  per account named `jianpu-outbox:<account>`, object store `records`,
  string key -> string value (`web/src/storage/outbox/outboxStore.ts`).
  Unsynced cloud edits live there, so the bridge must carry it too.
- Payload shape (opaque to the worker), version 1:
  `{ version: 1, localStorage: {key: value}, indexedDb: [{ name, records: [{key, value}] }] }`.
- Rust file store: `src/file_tree/store_state.rs` (`FileStoreState`), file
  ops in `src/file_tree/file_ops.rs`, unique names in
  `src/file_tree/unique_name.rs`; wasm exports in
  `crates/jianpu-wasm/src/component/guest_file_store.rs`, WIT in
  `crates/jianpu-wasm/wit/world.wit` (`file-store-state` record); TS calls
  via `jianpuWasm().fileStoreXxx` in `web/src/fileStore.ts`.
- `web/functions/index.ts` (Pages Function) rewrites OG tags for `?s=`
  share links. It is deployed with the bridge on the old Cloudflare project
  too (the bridge page has the same `og:` tags), so old links keep rich
  previews there. GitHub Pages only redirects (no data handoff).
